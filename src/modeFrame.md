# 騎乘模式切換協議（host ↔ AI 板）

對應程式：`src/modeFrame.js`、`src/modes/normal/useBleTelemetry.js`

App 透過 BLE 送文字指令 `CAN,<id 16進>,<dlc>,<byte0>,...`（換行結尾）給 AI 板，
由 AI 板轉成實體 CAN 幀。以下為模式切換相關的三個 ID。

---

## 曾經的問題（已解決，記錄備查）

**實測狀況：模式切換本身是成功的**（板子確實會進入對應模式運行），
但 App 端「等待確認」永遠逾時，畫面每次都跳「未收到運算板確認」。

原因是**舊規格表與韌體實作不符**，App 照舊規格表對，兩處都對錯：

| | 舊規格表（App 原本找的） | 韌體實際實作 |
|---|---|---|
| CAN ID | `0x1FA23000` | **`0x1FA13001`** |
| byte0 | `0xAA` | **`0xA5`** |

ID 不符 → 解析直接回 null → 等待者永遠不會被喚醒 → 必定逾時。
（SET_MODE `0x1FA13000` 是對的，所以模式真的有切換成功。）

App 已改為對照下方 ② 的實際協議。

---

## ① SET_MODE `0x1FA13000`（host → AI 板）

切換騎乘模式。**此段已實作且正常運作，不需更動。**

| Byte | 欄位 | 值 |
|---|---|---|
| 0 | ModeCode | `0x01` 一般 / `0x02` 電量管理 / `0x03` 智慧輔助 |

DLC = 1

送出範例：

```
CAN,1FA13000,1,01     一般模式
CAN,1FA13000,1,02     電量管理模式
CAN,1FA13000,1,03     智慧輔助模式
```

> 註：心肺模式不是獨立的切換模式，進入時送一般模式（`0x01`）。
> 舊規格表上寫的 `0x01~0x05` 是早期版本殘留，實際只有這三個。

---

## ② MODE_ACK `0x1FA13001`（AI 板 → host）✅ 已實作

收到 SET_MODE 後回一次。ID 是 **SET_MODE 的 ID + 1**。

| Byte | 欄位 | 值 |
|---|---|---|
| 0 | 固定值 | `0xA5`（收到並執行） |
| 1 | **回音**：本次請求的 ModeCode | `0x01~0x03` |

DLC = 2，格式即 `0xA5 + 模式碼`。

byte1 是「**這次請求的 ModeCode 回音**」，host 靠它配對這筆 ACK 是回應哪一次切換。

回覆範例：

```
ID=0x1FA13001 DLC=2 DATA=A5 01      收到「切到一般模式」
ID=0x1FA13001 DLC=2 DATA=A5 02      收到「切到電量管理模式」
ID=0x1FA13001 DLC=2 DATA=A5 03      收到「切到智慧輔助模式」
```

> 註：目前沒有定義失敗碼——收到 `0xA5` 即代表已接受並執行。
> 若之後要區分失敗，再約定一個非 `0xA5` 的值即可（App 端已把非 `0xA5` 視為失敗）。

---

## ③ MODE_STATE `0x1FA23001`（AI 板 → host）⬜ 提案中，韌體尚未實作

**每秒廣播目前生效模式。** 與 ② 分開，純狀態回報，與任何請求無關。

| Byte | 欄位 | 值 |
|---|---|---|
| 0 | 目前生效模式 | `0x01~0x03` |

DLC = 1

廣播範例：

```
ID=0x1FA23001 DLC=1 DATA=03         目前在智慧輔助模式
```

### 為什麼要這個

1. **更可靠的切換確認**——與其只信「板子說它收到了」，不如看「廣播的目前模式
   真的變成目標模式」才算成功。這反映實際狀態，比 ACK 更有保證。
2. **狀態同步**——App 隨時知道板子在哪個模式。若 App 以為在一般模式、
   板子其實在智慧輔助（例如中途重開機），畫面可以立刻提示不一致。

---

## App 端的相容處理

`useBleTelemetry` 已寫成**現在能跑、③ 加上去也自動生效**：

- 收到 ② MODE_ACK（`0x1FA13001`）：`byte0=0xA5` 且回音符合就確認；
  若沒帶 byte1（DLC=1）也接受，因為這個 ID 只有模式 ACK 在用，
  且同時間只會有一個等待者。
- 收到 ③ MODE_STATE（若韌體之後實作）：廣播的模式變成目標值即視為成功，
  不必等 ACK。
- 兩者任一成立就通過，逾時 8 秒才判定失敗。
- 等待者是「**先掛好再送指令**」，避免板子回太快時 ACK 落在註冊空窗期被錯過。

診斷面板（一般模式 → 診斷資訊）會把每一筆 ACK 的 ID、DLC、bytes 印出來，
格式為 `✓ 模式 ACK ok=true 回音=3`，方便對照。
